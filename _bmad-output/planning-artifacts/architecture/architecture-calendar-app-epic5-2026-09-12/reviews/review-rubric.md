パラダイム(Capacitor ラップ + プラットフォーム別ネイティブブリッジ + 共有ドメイン)自体は妥当で、親スペインの AD-1・AD-2・AD-6・AD-9・AD-10 を素直に延長できている。AD-11〜16 の切り分け(データブリッジ/ネイティブ UI、読み取り専用、クライアント発取り込み、通知ID導出、ディープリンク共通化)も筋が良い。

## 1. 決定点の網羅性(一段下の実装者が実際に分岐しうる点)

以下は AD/Convention/Deferred のどこにも書かれておらず、実装者が独自判断で埋めることになる箇所。

- **(a) ウィジェットのサイズ→件数マッピングの決定主体が未定。** FR-18 は「ウィジェットのサイズに応じて表示件数が変わる(1/2/3件)」を要求するが、AD-12 は「代表予定1〜3件分の…JSON」を push するとしか書いておらず、①JS側が常に最大3件を push してネイティブ側が自分のサイズに応じて何件見せるか切り詰める、②ネイティブ側が現在のウィジェットサイズをブリッジに伝えて `selectFeaturedEvents` の `limit` をその都度変える、のどちらの設計かが決まっていない。iOS 実装者と Android 実装者が別々の前提で作ると、片方は常時3件データを保持し他方は都度リクエストする、という非対称な実装になりうる。
- **(b) 端末カレンダーの「複数カレンダー」モデリングが未指定。** AD-13 は「`connections` テーブルの `provider = 'device'` 行」とだけ言うが、親スペインには接続1つに対し複数の外部カレンダーを紐づける `connection_calendars` テーブルと `sync_state`(カレンダー単位の成功/失敗記録、AD-4)が既に存在する。EventKit/CalendarContract もアカウント配下に複数カレンダーを持つ構造で、PRD FR-19 も「端末カレンダー一覧(名前・色)が表示され…個別にオン/オフ」を要求している。`connection_calendars` を端末カレンダーにも再利用するのか、`sync_state` 相当の記録を持つのかが本スペインのどこにも書かれておらず、iOS/Android 双方の実装者が別々のテーブル設計を持ち込むリスクがある。
- **(c) 権限拒否時のエラー表現経路が未指定。** FR-19 は「拒否された場合はその旨を表示し、機能を無効化するだけでアプリ全体は落とさない」と明示的にテスト可能な要求を出しているが、親スペインの `Result<T, AppError>` / `messageKey` 規約(Conventions「エラー形」)に端末カレンダー権限拒否がどう乗るのか、あるいは `src/platform` 独自のエラー型で処理するのかが未定義。既存の Google 接続エラーと表現が食い違う可能性がある。
- **(d) OS 通知権限(ローカル通知そのものの許可ダイアログ)への言及が皆無。** FR-19 のカレンダー権限拒否時の挙動は書かれているが、Android 13+ の通知権限や iOS の通知許可ダイアログを拒否された場合の扱い(FR-20)には一切触れていない。
- **(e) `connections.provider` のスキーマ制約変更が暗黙。** `provider = 'device'` という新しい値を許可するために、CHECK 制約や enum の変更が要るはずだが、Structural Seed / デプロイ節のどこにも migration の必要性が書かれていない。

## 2. AD の Rule 実行可能性(enforceable か、Prevents を実際に防げるか)

- AD-11〜AD-16 は総じて「呼び出し場所を1箇所に強制する」「特定のプラグイン/関数を名指しする」形になっており、コードレビューで機械的にチェックできる水準にある。良好。
- **AD-12 の「`capacitor-widget-bridge` 系のプラグインを使い自作しない」は「系」という言葉がやや曖昧。** Stack 表では具体名が1つ(`capacitor-widget-bridge`)しかないため実害は小さいが、「系」という表現は将来 fork や代替パッケージへの差し替えを無審査で許容しかねない。「このプラグイン(または後継のフォーク)に限る」等、線引きを明確にした方がよい。
- **AD-15 の通知ID導出(UUID→32bit int)は衝突ケースへの言及がない。** Prevents に書かれている「複数箇所で違うID導出ロジックが生まれて衝突する」(=ロジックの重複)は導出関数を1箇所に集約することで防げているが、「異なる予定が同じ32bit値にハッシュ衝突する」という別種の衝突は Rule でカバーされていない。個人利用規模(SM-6)なら実害は低いと推測されるが、衝突時に「別の予定の通知を誤って cancel/上書きする」という具体的な破損モードがあるため、最低限「衝突時は先勝ち/後勝ちのどちらか」を一文書いておくべき。
- AD-13/AD-14 は良好(「端末はサーバーから物理的にアクセス不能」という制約を根拠に AD-4 パターンを明示的に不適用とし、新パターンを立てている点は説明力が高い)。
- AD-16 も良好(ディープリンク受け口を1箇所に固定し、フォールバックの決定権も明示)。

## 3. Deferred の中に「非互換に作れてしまう」ものが混ざっていないか

- 概ね適切に Deferred へ回っている(ネイティブ実装そのもの、CI/CD、複数リマインダー、Android バックグラウンド定期同期は理由も妥当)。
- **「Doze・再起動に対する通知の高度な耐性」の行だけ性質が異なる。** 「v1 は `allowWhileIdle` 程度に留める」という記述は既に1つの設計判断であり、単なる先送りではない。この判断は AD-15 の Rule 本文には反映されておらず、Deferred 表の中に埋もれている。Android は再起動で `AlarmManager` ベースのスケジュールが消えるのが一般的な挙動であり、「再起動後にリマインダーが黙って鳴らなくなる」という PRD の testable consequence(予定削除でリマインダー取消、以外は特に規定なし)に対する黙示の劣化仕様になっている。実装者(Android担当)が独自に `BOOT_COMPLETED` レシーバーで再スケジュールする/しないを選べてしまう点で、"Deferred" というより "AD-15 に追記すべき決定" に近い。

## 4. 名指しされた技術のバージョン妥当性

- `@capacitor/core` 等 8.5.1 は「2026-09-12 npm 確認」と明記されており、Capacitor の年次メジャーリリースの流れ(6→2024, 7→2025, 8→2026 相当)から見て不自然ではない。パッチ番号までは検証しようがないが、確認日を明記している点は好ましい。
- `capacitor-widget-bridge` と `@ebarooni/capacitor-calendar` はいずれもコミュニティ製(非公式)プラグイン。Capacitor 8.x 対応・メンテナンス継続を前提にしているが、公式プラグインではない以上、着手直前に「実際に Capacitor 8 でビルドが通るか」「直近のコミット/リリースがあるか」を再確認するステップがどこにも明記されていない。AD-12/AD-14 は「自作しない」という方針は正しいが、非公式プラグインへの依存リスク(メンテ停止時の代替手段)への言及がない。
- `@capacitor/local-notifications` は公式 first-party なので妥当。
- iOS(SwiftUI/WidgetKit)・Android(Jetpack Glance/RemoteViews)は現行の標準的な選択で違和感なし。

## 5. 親スペイン AD-1〜10 との矛盾・弱体化の有無

- 直接矛盾する新規ADは無い。AD-4→AD-14 の置き換えも「サーバーは端末に物理アクセス不能」という理由が明示されており、弱体化ではなく正当な非適用として扱われている。
- **ただし「Inherited Invariants」表に AD-5・AD-7・AD-8 が抜けている。** AD-15 の Rule 本文は「AD-8 のサブタイプ属性と同じパターン」と明示的に AD-8 を参照しているのに、AD-8 は Inherited Invariants 表にも frontmatter の `binds` にも載っていない。同様に AD-7(UTC保存・表示時変換)はリマインダーの相対時刻計算やウィジェットの開始時刻表示に直接効く前提のはずだが、継承表に出てこない。AD-5(優先度は1か所の DB 関数経由)も `selectFeaturedEvents` の入力(`calendarPriority`)に暗黙に依存している。矛盾ではないが、継承関係の記載漏れであり、実装者が「Epic5 スペインに書いてないから AD-7/AD-8 は関係ない」と誤読するリスクがある。

## 7. このアーキテクチャ altitude が沈黙すべきでない次元(デプロイ・環境・運用)

「デプロイと環境(親スペインへの追加分)」節はビルド方法・配布経路(TestFlight/Play Console)までは書いてあるが、以下が沈黙している。

- **署名鍵・証明書の管理。** iOS の provisioning profile / Android のキーストアをどこで・誰が保持するか、紛失時に更新できなくなるリスクへの言及が無い。個人配布規模でも「鍵を失うと同じ app id で再配布できない」という運用上の落とし穴であり、最低限一文触れておくべき。
- **ネイティブビルドへの環境変数・シークレットの受け渡し方法。** 親スペインは Web ビルドのシークレット運用(anon key, OAuth client ID)を明記しているが、Capacitor のネイティブビルド(Xcode/Android Studio)にこれらをどう渡すか(ビルド時 env / native config ファイル等)の言及が無い。
- **アプリ更新の配布メカニズム。** 「CI/CDは Deferred、手動ビルド」とあるが、Web資産だけの変更(JSバンドル更新)を都度ストア審査に出すのか、何らかのライブ更新の仕組みを使うのか(使う場合は各ストアの規約適合の検討が要る)が未確定のまま。ここは軽くでも書いておかないと、ストーリー実装者が独自にライブ更新の仕組みを持ち込みかねない。
- **DB migration の言及。** `connections.provider` に新しい値を追加する以上、migration が必要なはずだが Structural Seed 節にその一言が無い(6-b/1-eと同根)。
- 一方で、ステージング環境・監視については親スペインの Deferred を明示的に継承しており、この点は沈黙ではなく意図的な先送りとして適切に扱われている。

## 推奨アクション(優先順)

1. **AD-12 のウィジェット push データ仕様を PRD と一致させる。** 「タイトル・時刻・色」→「カレンダー名・色・開始時刻」に修正し、必要なら予定タイトルを含めるかどうかも明記する。
2. **AD-15(または Capability Map)に、同期・取り込み経路(Google Edge Function upsert、AD-14 のクライアント発 upsert)がリマインダーの cancel/reschedule フックを必ず経由することを明記する。**
3. **ウィジェットのサイズ→件数決定の主体を1箇所に固定する Rule を追記する。**
4. **端末カレンダーの複数カレンダー選択 UI が拠って立つデータモデル(`connection_calendars` 再利用 or 新設)を明記する。**
5. Inherited Invariants 表に AD-5・AD-7・AD-8 を追加し、依存関係を可視化する。
6. デプロイ節に署名鍵管理・ネイティブビルドのシークレット受け渡し・アプリ更新メカニズムの方針を最低限一文ずつ追記する。
7. AD-15 に通知ID衝突時の扱いを一文追記する。AD-12 の「`capacitor-widget-bridge` 系」の表現を具体名限定に締める。
