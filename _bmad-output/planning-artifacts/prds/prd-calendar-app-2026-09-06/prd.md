# PRD: カレンダーアプリ(仮)
*作業タイトル — 確定待ち。候補: 「並べ替えられるカレンダー」「PrioriCal」。*

## 1. ビジョン

複数のカレンダー(このアプリで作った予定、Google カレンダー、いずれは端末 OS のカレンダー)を1つのビューに集約するカレンダーアプリ。既存アプリと決定的に違うのは、**カレンダーごとに「優先度」を設定でき、その優先度が表示に効く**こと。

優先度は表示に2通りに作用する。ひとつは並び順 ── カレンダー一覧や予定リストが優先度順に並ぶ。もうひとつは代表予定の選抜 ── ウィジェットや時計盤面のように表示枠が狭い場面で、優先度の高いカレンダーの予定を「代表予定」として前に出す。既存のカレンダーアプリは購読中のすべての予定を対等に扱うため、狭い画面で本当に大事な予定が些末な予定に埋もれる。このアプリはそこを正面から解決する。

あわせて、シフト勤務者向けに「お気に入りシフト」からのワンタップ入力と、当月の給料見込みの表示を v1 から載せる。まず Web アプリとして作り、その後スマートフォンアプリ化して一般配布する。

## 2. 対象ユーザー

### 2.1 Jobs To Be Done

- 仕事・プライベート・家族の共有カレンダーを、アプリを行き来せず1画面で見たい。
- ウィジェットやスマートウォッチのような狭い表示枠でも、「外せない予定」を必ず先頭に出したい。
- バイトのシフトを毎回打ち込まず、登録済みテンプレから一瞬で入れたい。
- 今月の給料がいくらになるか、アプリを開くだけで分かるようにしたい。
- (作り手として)自分のカレンダーの使い方に合った道具を持ちたい。

### 2.2 v1 の非ユーザー

- 店舗・チームのシフトを**組む**人。従業員割り当て・勤怠管理は対象外(§5)。
- Google 以外(Outlook / iCloud / 任意の .ics URL)のカレンダーだけを使っている人。v1 の外部接続は Google のみ。
- カレンダーを1つしか使わない人。優先度の価値が出ないため、v1 の主対象ではない。

### 2.3 主要ユーザージャーニー

- **UJ-1. 圭太が家を出る前に、今日の"外せない予定"だけ確認する。**
  - **人物 + 状況:** 圭太、会社員。仕事・私用・部活の共有カレンダーを3つ使い分けている。前回セッションで認証済み。
  - **入口:** スマホのホーム画面(v1 Web ではブラウザのブックマーク/PWA アイコン)。アプリの「コンパクトビュー」を開く。
  - **経路:** コンパクトビューが、優先度が最も高い「仕事」カレンダーの次の予定を1件、大きく表示。その下に次点を2件。細かい部活の連絡予定は畳まれている。
  - **クライマックス:** 「10:00 役員会議」が一番上にあると一目で分かる。他の予定に埋もれていない。
  - **解決状態:** 圭太はアプリを閉じて家を出る。会議を忘れない。
  - **エッジケース:** 同じ「仕事」カレンダーに 10:00 の予定が2件あるとき、選抜ロジック(FR-9)で1件が代表になる。

- **UJ-2. 圭太が Google の3つのカレンダーを取り込んで、優先順位をつける。**
  - **人物 + 状況:** 初回セットアップ中。Google アカウントは1つ、その中に「個人」「仕事」「部活(共有)」の3カレンダー。
  - **入口:** 設定 → カレンダーを接続 → Google。
  - **経路:** OAuth で Google を認可 → 取り込む3カレンダーを選ぶ → 一覧に3つ並ぶ → ドラッグで「仕事 > 個人 > 部活」の順に優先度をつける。
  - **クライマックス:** 統合ビューで、同じ時間に重なった予定が優先度順に描画され、コンパクトビューの代表予定が「仕事」から選ばれるようになる。
  - **解決状態:** 以降、取り込みは自動。優先度はいつでも変えられる。

- **UJ-3. 美咲が1週間分のシフトを入れて、今月の見込み額を見る。**
  - **人物 + 状況:** 美咲、大学生。カフェのバイト。時給1,100円、平日は17:00–22:00(休憩30分)、土曜は9:00–18:00(休憩60分)の2パターン。
  - **入口:** 月表示のカレンダー。「お気に入りシフト」に2パターン登録済み。
  - **経路:** 平日の日付を5つタップ → それぞれ「平日シフト」をワンタップ選択 → 土曜をタップ →「土曜シフト」を選択。
  - **クライマックス:** トップ画面の「当月の給料見込み」が入力するたびに増える(この1週間分で 平日 4.5h×5 + 土曜 8h、いずれも時給1,100円)。
  - **解決状態:** 電卓も別アプリも使っていない。シフト予定はカレンダーにも「シフト用カレンダー」の予定として並ぶ。
  - **エッジケース:** 深夜0時をまたぐシフトは、日付をまたいでも1勤務として実働時間を計算する(FR-13)。

- **UJ-4. 圭太が端末のカレンダーも取り込んで、Google と同じ画面で見る。**(Epic 5) `[ASSUMPTION: 2026-09-12 のバッチ質問への回答から推測。Ryo の実際のシナリオと違えば修正。§10]`
  - **人物 + 状況:** 圭太、スマホアプリ版に移行済み。家族共有カレンダーは Google 非対応で、端末(OS)のカレンダーにだけ入っている。
  - **入口:** 設定 → カレンダーを接続 → 端末カレンダー。
  - **経路:** OS の権限ダイアログで許可 → 端末カレンダー一覧が表示される → 「家族」だけをオンにする → 優先度を並べ替える。
  - **クライマックス:** 統合ビューに「家族」の予定が Google の予定と混ざり、優先度どおりに並ぶ。
  - **解決状態:** アプリを行き来せず、1画面にすべてのカレンダーが集まる(FR-19)。

- **UJ-5. 美咲が土曜のシフトだけリマインダーを付ける。**(Epic 5) `[ASSUMPTION: 同上。§10]`
  - **人物 + 状況:** 美咲、シフト勤務者。平日のシフトは覚えているが、土曜だけ寝坊しがち。
  - **入口:** シフト予定の詳細画面。
  - **経路:** 「リマインダーを追加」→ プリセットの「1時間前」を選ぶ(または任意の分数を入力)。
  - **クライマックス:** シフト当日、通知で気づいて寝坊せず出勤できる。
  - **解決状態:** 全予定に自動で通知が付くわけではなく、必要な予定だけに個別設定している(FR-20)。

## 3. 用語集

*後続工程と読者はこの用語をそのまま使う。PRD 内で同義語を持ち込むのは規律違反。*

- **カレンダー** — 予定の集合。source が **ローカル**(このアプリで作成)か **外部接続**(Google 等から取り込み)かのいずれか。カレンダーは1つの **優先度** を持つ。
- **予定** — 開始時刻と終了時刻、または「終日」フラグを持つ項目。ちょうど1つの **カレンダー** に属す。
- **外部接続** — 外部サービス(v1 は Google のみ)のアカウント連携。1つの外部接続が複数の外部 **カレンダー** を **取り込み** 対象にできる。
- **取り込み** — 外部 **カレンダー** の **予定** を読み取り専用でローカルに反映する、定期的な一方向同期。このアプリから外部へは書き戻さない(v1)。
- **優先度** — **カレンダー** ごとに付ける順位(1 が最上位)。**並び順** と **代表予定** の選抜に作用する。
- **並び順** — カレンダー一覧・予定リスト・時間帯が重なった予定の描画順が **優先度** に従うこと。
- **代表予定** — 表示枠が限られる場面で、**選抜ロジック** により前に出す1〜数件の **予定**。
- **選抜ロジック** — 代表予定を決める規則(FR-9)。
- **コンパクトビュー** — **代表予定** だけを表示する最小ビュー。アプリ内の画面・**ウィジェット** が同じ選抜結果を共有する。
- **ウィジェット** — スマートフォンのホーム画面に置く小型表示。**コンパクトビュー** をホーム画面に出したもの。ネイティブアプリ機能(§4.6, §8 参照)。
- **端末カレンダー** — スマートフォン本体(OS)が持つカレンダー。**外部接続** の一種として **取り込み** 対象にできる(§4.6)。
- **リマインダー** — **予定** ごとに任意で設定する、端末のローカル通知(§4.6)。**選抜ロジック** とは独立。
- **お気に入りシフト** — 開始・終了・休憩(分)・時給・勤務先ラベルを持つ、再利用可能なテンプレート。
- **シフト** — **お気に入りシフト** から作られた **予定**。**給料見込み** の計算対象。ローカルの「シフト用カレンダー」に属す。
- **勤務先** — **シフト** に付くラベル。v1 では表示上の区別のみ(勤務先別の集計は v2)。
- **実働時間** — 終了 − 開始 − 休憩(分)。日をまたぐ **シフト** でも分割せず通算する。
- **給料見込み** — 指定した月に含まれる **シフト** の(**実働時間** × 時給)の合計。

## 4. 機能

### 4.1 カレンダー統合ビュー

**説明:** ローカルの予定と、外部接続から取り込んだ予定を、1つのカレンダー画面に集約して表示する。月表示・週表示・リスト表示を切り替えられる。各カレンダーは表示のオン/オフを切り替えられる。UJ-1・UJ-2 を実現する。外部接続は v1 では Google のみ。取り込みは読み取り専用。

**Functional Requirements:**

#### FR-1: ローカル予定の作成・編集・削除

ユーザーは、ローカルカレンダーに予定(タイトル、開始/終了 または終日、メモ、所属カレンダー)を作成・編集・削除できる。

**Consequences (testable):**
- 開始時刻が終了時刻より後の予定は保存できず、エラーを表示する。
- 終日予定は時刻を持たず、日付範囲(1日以上)で保持される。
- 削除は確認ダイアログを経て、取り消し(Undo)を一定時間提示する。

#### FR-2: カレンダー表示の切り替え(月 / 週 / リスト)

ユーザーは、月・週・リストの3ビューを切り替えられ、任意の日付へ移動できる。

**Consequences (testable):**
- どのビューでも、表示中のすべての「表示オン」のカレンダーの予定が見える。
- リストビューは、日付昇順、同一時間帯内は優先度順(FR-8)で予定を並べる。

#### FR-3: 外部接続(Google カレンダー)

ユーザーは、Google アカウントを OAuth で接続し、そのアカウント内のどのカレンダーを取り込むか選択できる。

**Consequences (testable):**
- 要求する OAuth スコープは、カレンダーの読み取りに必要な最小限に限る(§8.3)。書き込みスコープは要求しない。
- 接続後、取り込み対象カレンダーの一覧(名前・色)が表示され、個別にオン/オフできる。
- ユーザーは接続をいつでも解除でき、解除すると取り込んだ予定はローカルから消える。

#### FR-4: 取り込み(定期同期)

システムは、接続済みの外部カレンダーの予定を定期的に取り込み、統合ビューに反映する。

**Consequences (testable):**
- 取り込みは読み取り専用。取り込んだ予定はアプリ内で編集できない(閲覧のみ、編集 UI を出さない)。
- 各カレンダーについて「最終取り込み時刻」を表示する。
- 手動で「今すぐ取り込み」を実行できる。
- 取り込みに失敗したカレンダーは、その旨を一覧に表示する(他カレンダーの表示は止めない)。

**Out of Scope:**
- 外部カレンダーへの予定の書き戻し・作成・変更(v2)。
- Google 以外のサービス、任意の .ics URL 購読(v2)。

#### FR-5: カレンダーの管理

ユーザーは、ローカルカレンダーを作成・改名・色変更・削除でき、すべてのカレンダー(ローカル + 取り込み)を1つの一覧で見られる。

**Consequences (testable):**
- 一覧は各カレンダーの source(ローカル / Google)を明示する。
- 「シフト用カレンダー」は既定で1つ存在し、削除できない(改名・色変更は可)。

---

### 4.2 優先度と表示制御(コア)

**説明:** このアプリの唯一の勝ち筋。各カレンダーに優先度(順位)を与え、それを「並び順」と「代表予定の選抜」の両方に効かせる。UJ-1・UJ-2 を実現する。

**Functional Requirements:**

#### FR-6: カレンダーごとの優先度設定

ユーザーは、カレンダー一覧上でドラッグ操作等により、すべてのカレンダー(ローカル + 取り込み)に順位をつけられる。

**Consequences (testable):**
- 優先度は全カレンダーで一意の順序(同順位なし)。
- 新しく追加・取り込まれたカレンダーは、既定で最下位の優先度に入る。
- 優先度の変更は、並び順(FR-8)と代表予定(FR-9)に即時反映される。

#### FR-7: 予定の視覚的な優先表示

同じ時間帯に複数の予定が重なるとき、統合ビュー(週・月)は優先度の高いカレンダーの予定を、より目立つ位置・前面に描画する。

**Consequences (testable):**
- 週ビューで時間が重なる予定は、優先度が高いカレンダーのものを左端に置く。左右に並べきれず前後関係になる場合は、優先度が高いものを前面にする。
- 月ビューで1日のマスに入りきらない予定がある場合、優先度が高い予定から表示し、あふれた分は「他 N 件」に畳む。
- 「他 N 件」を開くと、その日の全予定を優先度順(同順は開始時刻順)で見られる。

#### FR-8: 優先度順の並び

カレンダー一覧・予定リスト・コンパクトビューの並びは、優先度に従う。

**Consequences (testable):**
- リストビュー / コンパクトビューで、同一日時の予定は優先度が高いカレンダーのものが上。
- 優先度を変えると、再読み込みなしに並びが更新される。

#### FR-9: 代表予定の選抜(コンパクトビュー)

システムは、限られた表示枠(既定 1〜3 件)に出す代表予定を、選抜ロジックで決める。

**選抜ロジック(v1):**
1. 現在時刻以降に始まる(または進行中の)予定のみを対象にする。
2. 優先度が高いカレンダーの予定を、低いカレンダーの予定より先に出す(優先度がまず効く)。
3. 同じカレンダー内では、開始時刻が早い順。 `[ASSUMPTION: 全体規則は「優先度 → 開始時刻が早い順」。対案は「優先度 → 今から近い順」。この違いで、低優先度カレンダーの直近予定を代表に含めるかが変わる。§9-1]`
4. 終日予定は、時刻付き予定をすべて出し切ってから、下位に回す。 `[ASSUMPTION: 終日予定の扱い。§9-1]`
5. 表示枠の件数(既定 3、ウィジェットのサイズで 1/2/3 可変)に達したら打ち切る。

**Consequences (testable):**
- コンパクトビューは常に「今日以降」の予定のみを出す(過去の予定は出さない)。
- 対象予定が0件のとき、「次の予定なし」を表示する。
- アプリ内のコンパクトビューとウィジェット(FR-18)は同じ選抜結果を返す(選抜は1か所で実装)。 `[更新 2026-09-12: 当初「通知も同じ選抜結果を使う」としていたが、FR-20 でリマインダーは予定ごとの個別設定に変更したため対象から外した。§10]`

#### FR-10: コンパクトビュー画面

ユーザーは、アプリ内でコンパクトビューを1画面として開ける(v1 Web でのウィジェット代替)。

**Consequences (testable):**
- 代表予定(FR-9)を、統合ビューより低い情報密度で(1件ずつ独立した行/カードで)、優先度順に表示する。
- 各予定にカレンダー名・色・開始時刻を添える。
- 予定をタップすると統合ビューの該当日へ遷移する。
- 表示件数(1〜3)を設定で選べる。

---

### 4.3 シフト入力

**説明:** シフカレのような「楽な入力」。よく使うシフトをテンプレ(お気に入りシフト)として登録し、カレンダー上でワンタップで日付に置く。UJ-3 を実現する。

**Functional Requirements:**

#### FR-11: お気に入りシフトの登録

ユーザーは、お気に入りシフト(名前、開始時刻、終了時刻、休憩分、時給、勤務先ラベル、色)を登録・編集・削除できる。

**Consequences (testable):**
- 複数のお気に入りシフトを持てる(件数上限なし、現実的には数件)。
- 時給・休憩分は数値バリデーションを行う(負値不可、休憩 < 実働)。

#### FR-12: ワンタップ・シフト入力

ユーザーは、カレンダーの日付を選び、お気に入りシフトを1つ選ぶだけで、その日にシフトを作成できる。

**Consequences (testable):**
- 作成されたシフトは「シフト用カレンダー」に属す予定として統合ビューに並ぶ。
- 同じ日に複数シフトを入れられる。
- 連続する複数日を選んで同じお気に入りシフトを一括適用できる。 `[ASSUMPTION: 複数日一括はv1に含める。§9-2]`
- 作成後、シフト個別に開始/終了/休憩を上書き編集できる(元のお気に入りシフトは変えない)。

#### FR-13: シフトの実働時間計算

システムは、各シフトの実働時間を「終了 − 開始 − 休憩」で求める。

**Consequences (testable):**
- 終了時刻が開始時刻より前(日をまたぐ)の場合、終了を翌日として通算する。分割はしない。
- 実働時間は分単位で保持し、給料計算では時間に換算する。

---

### 4.4 簡易給料計算

**説明:** v1 は「時給 × 実働時間」の月合計のみ。深夜/早朝割増、休日、締め日、給料日、勤務先別、年別集計は v2 以降(§5、§6.2)。UJ-3 を実現する。

**Functional Requirements:**

#### FR-14: 当月の給料見込み

システムは、指定された月の給料見込み(その月のシフトの実働時間 × 時給 の合計)を計算する。

**Consequences (testable):**
- 月の区切りは暦月(1日〜末日)。 `[ASSUMPTION: 締め日設定なし。§9-3]`
- シフトごとに時給が異なる場合(お気に入りシフト由来 + 個別上書き)、それぞれの時給で計算して合算する。
- 対象月にシフトが0件なら ¥0 を表示する。

#### FR-15: トップ画面での見込み表示

ユーザーは、アプリのトップ画面で、追加操作なしに当月の給料見込みを確認できる。

**Consequences (testable):**
- 表示は当月。前月・翌月へ切り替えられる。
- シフトを追加・編集・削除すると、金額が即時に更新される。

### 4.5 アカウントとデータ

**説明:** 外部接続(Google OAuth)と、複数端末での利用のために、アカウントの概念を持つ。データ保管方式は未確定(§9-4)で、この節の FR は方式に依存しない書き方にしている。

**Functional Requirements:**

#### FR-16: サインアップ / ログイン

ユーザーは、アカウントを作成してログインできる。 `[ASSUMPTION: メール + パスワードのアカウント制。ローカル完結案なら不要になる。§9-4]`

**Consequences (testable):**
- 未ログインでは、ローカル予定の作成と閲覧まではできる。 `[ASSUMPTION: お試し利用を許す。§9-4]`
- Google 外部接続にはログインが必要。
- ログアウトできる。

#### FR-17: データの持ち出し(エクスポート)

ユーザーは、自分のローカルカレンダー・予定・お気に入りシフトを JSON でエクスポートできる。

**Consequences (testable):**
- エクスポートにはローカルで作成したデータのみを含む(取り込んだ外部予定は含めない)。

**Notes:**
- `[NOTE FOR PM]` 複数端末同期・インポートは §9-4(保管方式)の決定後に FR 化する。

### 4.6 スマホアプリ化(Epic 5)

**説明:** v1(Web)の資産を Capacitor 等でネイティブアプリにラップし、ブラウザからは提供できない3つの OS ネイティブ機能を追加する: ホーム画面ウィジェット、端末カレンダーの取り込み、リマインダー通知。優先度(§4.2)・選抜ロジック(FR-9)はここでも同じものをそのまま再利用し、新しい判断基準を持ち込まない。Android・iOS 両対応。UJ-1(狭い表示枠でも「外せない予定」を先頭に出す)の完成形であり、UJ-4・UJ-5 を実現する。 `[ASSUMPTION: ラップ方式は Capacitor が第一候補(addendum.md)。アーキテクチャ工程で正式に確定。§10]`

**Functional Requirements:**

#### FR-18: ホーム画面ウィジェット

ユーザーは、スマートフォンのホーム画面にウィジェットを置き、アプリを開かずに代表予定を確認できる。

**Consequences (testable):**
- ウィジェットは選抜ロジック(FR-9)の結果をそのまま表示する。アプリ内コンパクトビュー(FR-10)と同じ代表予定・同じ並び順になる(選抜は1か所で実装、という FR-9 の原則を継承)。
- ウィジェットのサイズに応じて表示件数が変わる(1 / 2 / 3 件、FR-9 の既定と同じ)。
- 各行にカレンダー名・色・開始時刻を表示する(FR-10 と同じ情報密度)。
- ウィジェットをタップするとアプリが開き、該当予定(または該当日)へ遷移する。
- 対象予定が0件のとき、感嘆符のない静かな表示にする(コンパクトビューの「次の予定なし」に準じる、NFR12 相当)。
- Android(App Widget 相当)・iOS(WidgetKit 相当)の両方で提供する。 `[ASSUMPTION: 両プラットフォーム同時対応。§10]`
- ウィジェットの更新頻度は OS のバックグラウンド更新制約に従う(アプリ本体ほどの即時性は保証しない)。具体的な更新間隔・トリガーはアーキテクチャ工程で確定。

**Out of Scope:**
- ウィジェットのレイアウト・配色のカスタマイズ。
- ウィジェットからの直接操作(予定作成・編集・シフト入力)。閲覧専用(FR-10 と同じ立て付け)。

#### FR-19: 端末カレンダーの取り込み

ユーザーは、スマートフォン本体(OS)のカレンダーを、Google と同様に外部接続の一種として取り込み対象に選択できる。

**Consequences (testable):**
- 端末カレンダーは「外部接続」の一種として扱う。取り込みは読み取り専用(FR-4 と同じ原則。§8.3 の一方向性の要件をそのまま適用)。
- OS のカレンダーアクセス許可を明示的に要求する。拒否された場合はその旨を表示し、機能を無効化するだけでアプリ全体は落とさない。
- 接続後、端末カレンダー一覧(名前・色)が表示され、Google の取り込み対象選択(FR-3)と同じ操作感で個別にオン/オフできる。 `[ASSUMPTION: Google と同じ「選択制」UI パターンを踏襲(全カレンダー自動取り込みにはしない)。§10]`
- 取り込んだ予定は統合ビューの他の予定と同列に扱われ、優先度(FR-6〜FR-9)がそのまま効く。
- 接続を解除すると、取り込んだ予定はローカル(このアプリの DB)から削除される(FR-3 と同じ挙動、§8.3)。

**Out of Scope:**
- 端末カレンダーへの書き戻し(v1 の Google 接続と同じ理由で対象外、§8.3)。
- Android(CalendarContract 相当)と iOS(EventKit 相当)の API 差異の吸収方法はアーキテクチャ工程で確定。

#### FR-20: リマインダー通知

ユーザーは、予定ごとに個別のリマインダー通知を任意で設定できる。

**Consequences (testable):**
- 既定は通知オフ。全予定に自動で付くのではなく、予定ごとのオプトインで設定する。
- 通知タイミングはプリセット(10分前 / 30分前 / 1時間前)、またはユーザー定義の任意の分数から選べる。
- 対象は予定の source を問わない(ローカル・Google 取り込み・端末カレンダー取り込みのいずれの予定にも設定できる)。
- 通知は端末のローカル通知として、予定時刻から逆算してスケジュールする(サーバー起点の push 配信ではない)。 `[ASSUMPTION: ローカル通知のみ。push 配信サーバーは持たない。アーキテクチャ工程で確定。§10]`
- 通知をタップするとアプリが開き、該当予定の詳細へ遷移する。
- 予定の開始・終了時刻を編集すると、設定済みのリマインダー(相対時間)は新しい時刻を基準に再スケジュールされる。取り込んだ予定が同期で時刻変更された場合も同様。
- 予定を削除すると、設定済みのリマインダーも取り消される。

**Out of Scope:**
- 選抜ロジック(FR-9)の結果をそのまま使う「代表予定のダイジェスト通知」は、今回は採用しない。 `[NOTE FOR PM: 当初の v1 PRD(§6.2)は「選抜結果をそのまま通知に使う」という設計意図を残していたが、本更新でユーザーの意向により予定ごとの個別設定へ置き換えた。ダイジェスト型通知は将来の検討候補として残す。§10]`
- 繰り返し予定の各回に個別のリマインダーを設定する UI(繰り返し予定の作成自体が §6.2 でスコープ外)。

## 5. Non-Goals(明示)

- **チーム / 店舗向けのシフト管理にはならない。** 従業員へのシフト割り当て、勤怠打刻、労務管理は作らない。あくまで個人が自分の予定とシフトを記録する道具。
- **汎用のプロジェクト管理・タスク管理にはならない。** ToDo、締め切り管理、リマインダーの作り込みは v1 の狙いではない。
- **外部カレンダーの"編集クライアント"にはならない(v1)。** 取り込みは読み取り専用。Google 側の予定をこのアプリから変更する機能は v1 では作らない。
- **精緻な給与計算ソフトにはならない(v1)。** 税・保険料の控除、年末調整、給与明細の発行は対象外。
- **スマートウォッチのネイティブアプリは v1 では作らない。** §8 参照。

## 8. プラットフォームと制約

### 8.1 プラットフォームの段階

- **v1 — Web アプリ。完了(2026-09-11)。** レスポンシブ、スマホブラウザ最適化、PWA インストール対応。外部接続は Google のみ。ウィジェットは無し(コンパクトビュー画面で代替)。
- **Epic 5(旧 v1.5)— スマートフォンアプリ展開。** Web の資産を活かしてスマホアプリ化する。**ホーム画面ウィジェット(FR-18)**、**端末カレンダー取り込み(FR-19)**、**リマインダー通知(FR-20)** が入る。**Android・iOS 両方を同時に対象とする**(2026-09-12 ユーザー決定)。 `[ASSUMPTION: Web資産を再利用するラップ方式(Capacitor が第一候補、addendum.md)。正式な確定と各プラットフォームの実装方式(App Widget / WidgetKit、CalendarContract / EventKit 等)はアーキテクチャ工程で。§9-4]`
- **v2+ — スマートウォッチ表示。** ネイティブ盤面アプリ、またはコンパクトビュー相当を外部カレンダーへ書き戻して既存ウォッチアプリに見せる(どちらが本命かはブリーフの通り未決)。Epic 5 のスコープには含まない。

### 8.2 配布

最終的に一般配布(ストア公開を想定)。無料。課金の有無は未定(§9-6)。

### 8.3 プライバシーと制約

カレンダーは私的な情報の塊であり、v1 から外部接続と一般配布を想定するため、以下を要件として固定する。

- **最小権限。** Google 連携で要求するのは読み取りに必要な OAuth スコープのみ(FR-3)。書き込み・連絡先・その他のスコープは要求しない。
- **読み取り専用。** 取り込んだ外部予定を、このアプリが外部サービスへ書き戻す・変更することは v1 では一切しない(FR-4)。
- **接続解除でデータを残さない。** 外部接続を解除したら、そのアカウント由来の取り込み予定はローカルから削除する(FR-3)。
- **持ち出しできる。** ユーザーは自分のローカルデータを JSON でエクスポートできる(FR-17)。
- **第三者へ渡さない。** 取り込んだカレンダー内容・予定本文を、広告その他の目的で外部に送信しない。
- **保管場所は要確定。** クラウド保管にする場合、ユーザーごとのデータ分離(行レベルの権限)と、OAuth トークンの安全な保持方式をアーキテクチャで決める(§9-4)。
- **端末カレンダーも同じ原則。** OS カレンダーの取り込み(FR-19)は Google 接続と同じ最小権限・読み取り専用・接続解除で削除の3原則に従う。OS の権限ダイアログで明示的に許可を得る。
- **通知はローカル完結。** リマインダー(FR-20)は端末側でスケジュールし、予定本文を外部の通知配信サーバーへ送らない。

5. **ローカルの繰り返し予定(§6.2)** — v1 で作成 UI を持つか。取り込んだ繰り返し予定の展開表示は v1 で必要。
6. **課金モデル(§7, §8)** — 完全無料か、将来の有料プラン(広告除去・精緻な給料計算等)を見込むか。

8. **iOS の配布要件(Epic 5、§8.1, §8.2)** — Apple Developer Program(年額登録)と審査プロセスが要る。Android は無料・審査なしで実機配布できる。両プラットフォーム同時進行を選んだ場合、この非対称がスケジュール・費用に響く。 `[NOTE FOR PM: 決定は不要だが、着手前に把握しておく]`
