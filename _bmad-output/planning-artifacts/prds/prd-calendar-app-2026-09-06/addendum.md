# 付録 — PRD に載せない技術・検討メモ

PRD 本文は「能力(何ができるか)」に絞っている。ここには実装寄りの検討、代替案、後続工程(アーキテクチャ / UX)が必要とする材料を置く。

## 技術スタックの第一候補([ASSUMPTION] ── ユーザー回答は「おまかせ」)

| 層 | 第一候補 | 理由 |
|---|---|---|
| フロント | Next.js + React + TypeScript + Tailwind CSS | human-book と同構成。既存の開発環境・ノウハウ・ハマりどころが流用できる |
| スマホ化 | Capacitor で Web をラップ | React Native 書き直し不要。CRUD 中心アプリに RN の重さは不要(human-book の判断と同じ) |
| データ保管 | Supabase(Postgres + 認証 + RLS) | 複数端末同期・配布・OAuth トークン保管・将来のウィジェット連携に適合。human-book で実績 |
| 外部接続 | Google Calendar API(OAuth 2.0、`calendar.readonly` 相当の最小スコープ) | v1 は読み取り専用のため書き込みスコープは要求しない |

**アーキテクチャ工程で確定すること:**
- データ保管を Supabase(クラウド)にするか、端末内完結(例: IndexedDB / SQLite)にするか。PRD §9-4。
- Google OAuth のトークンをどこに保持し、取り込みの定期同期をどこで走らせるか(クライアント / サーバー / スケジューラ)。
- 静的エクスポート(human-book で `output: export` と動的ルートの相性問題があった)を踏むか、サーバーを持つか。

## 代替案の検討メモ

### スマホ化の方式
- **Capacitor(採用候補)** — Web 資産再利用。ウィジェット・通知・端末カレンダーはネイティブプラグイン or ブリッジで対応。
- **Flutter / React Native で書き直し** — ウィジェットやウォッチ対応はネイティブに寄せやすいが、Web 先行方針と二重開発になる。却下寄り。
- **PWA のみでスマホ対応** — ホーム画面ウィジェット(iOS/Android のネイティブウィジェット)は PWA からは提供できない。コアの動機を満たせないため不十分。

### データ保管
- **Supabase(クラウド)** — 複数端末で同じカレンダー・優先度・シフトを見られる。配布時に各ユーザーのデータを分離(RLS)。サーバー依存。
- **端末内完結** — サーバー不要・プライバシー上シンプル。ただし複数端末で優先度やシフトが同期しない。Google OAuth のトークンをクライアントだけで安全に扱う設計難度が上がる。
- 中間案: ローカルファースト + 任意でクラウド同期。実装コスト高。

### 選抜ロジック(FR-9)の代替
- **優先度 → 開始時刻が早い順(採用候補)** — 予測しやすい。「次に何がある」を素直に返す。
- **優先度 → 今から近い順** — 進行中〜直近を強調。数分後に迫った予定を見逃しにくいが、開始済みの長い予定の扱いが要検討。
- **重なり枠は複数表示** — 枠を消費するため「1件だけ大きく」というコンパクトビューの狙いと相性が悪い。

## 競合(シフカレ)の機能要点 ── 給料計算 v2 の設計材料

web 調査(2026-09-06)。v1 では扱わないが、v2 の給料計算を設計するときのチェックリスト:

## UX 工程への申し送り

- コアの価値(優先度が表示に効く)が最も伝わるのは **コンパクトビュー / ウィジェット**。UX はここを主役に据える。
- **優先度の設定 UI** はドラッグでの並べ替えを想定(FR-6)。カレンダー一覧画面がそのまま優先度設定画面を兼ねる。
- **ワンタップ・シフト入力**(FR-12)の操作数が SM-3(3タップ以内)を満たすフローを設計する。
- v1 は Web / スマホブラウザ。狭い画面での月・週ビューの優先表示(FR-7)の見せ方が難所。
